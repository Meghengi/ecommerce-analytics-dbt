# ecommerce-analytics-dbt

A small, self-contained **dbt** project that models a direct-to-consumer
ecommerce business — customers, orders, and order line items — into
analytics-ready marts. Built to run anywhere with zero setup: no
warehouse, no credentials, no Docker. It uses [DuckDB](https://duckdb.org/)
as the local database engine, so `dbt build` runs end to end on a laptop
in seconds.

## Why this exists

This is a portfolio project demonstrating a standard dbt workflow on a
generic retail domain: staged sources, a conformed dimensional mart,
tests on every model, and documentation. It's deliberately scoped small
enough to read in one sitting.

## Data model

```
seeds/raw_customers      seeds/raw_products
seeds/raw_orders         seeds/raw_order_items
        │                        │
        ▼                        ▼
  staging/stg_*  (clean, rename, cast — 1:1 with sources)
        │
        ▼
  marts/fct_order_items  (grain: one row per order line item)
        │
        ├──► marts/dim_customers       (lifetime value + segment)
        ├──► marts/dim_products        (lifetime units/revenue)
        └──► marts/agg_monthly_revenue (monthly revenue & margin by category)
```

- **Staging layer** (`models/staging/`): one view per source, renamed and
  typed, no business logic.
- **Marts layer** (`models/marts/`): `fct_order_items` is the fact table
  at line-item grain; `dim_customers` and `dim_products` roll it up into
  dimensional summaries; `agg_monthly_revenue` is a pre-aggregated table
  for a BI tool to hit directly.
- **Tests**: `not_null`/`unique` on every primary key, `relationships`
  tests enforcing referential integrity between seeds, `accepted_values`
  on enumerated columns, and one singular test
  (`tests/assert_no_negative_margins.sql`) encoding a business invariant
  that generic schema tests can't express.
- **Macro**: `macros/safe_divide.sql` guards a margin-percentage
  calculation against divide-by-zero, and is written to be portable to a
  real warehouse (not relying on DuckDB-specific null behavior).

## Data

All data under `seeds/` is **synthetic**, generated by
`scripts/generate_seed_data.py` (Python standard library only — no
third-party packages, no network). Re-running it regenerates the same
rows every time (seeded RNG), so the dataset is reproducible:

```bash
python3 scripts/generate_seed_data.py
```

It produces 400 customers, 25 products across 5 categories, 2,200
orders, and ~4,100 order line items spanning Feb 2024–Dec 2025.

## Running it

Requires Python 3.9+ and pip with normal internet access (to install
dbt itself — the project's own data and logic need nothing else):

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install dbt-core dbt-duckdb

dbt seed    # loads the CSVs in seeds/ into DuckDB
dbt run     # builds staging views + mart tables
dbt test    # runs all schema + singular tests
# or just:
dbt build
```

dbt finds the `profiles.yml` in the project folder automatically when you
run it from the project root. This creates a local `ecommerce_analytics.duckdb`
file — nothing leaves your machine. dbt builds into three schemas:
`main_raw` (seeds), `main_staging` (views), and `main_marts` (tables).

### Poking around the result

Install the DuckDB command-line tool (`brew install duckdb` on a Mac,
`winget install DuckDB.cli` on Windows), then open the database:

```bash
duckdb ecommerce_analytics.duckdb
```

```sql
select customer_name, lifetime_revenue, customer_value_segment
from main_marts.dim_customers
order by lifetime_revenue desc
limit 5;
```

Type `.quit` to leave DuckDB. Close it before running dbt again, since
only one program can write to the database file at a time.

```
├── seeds/                        # synthetic source data (CSV)

├── models/

```

## Notes on the design

- **DuckDB over Snowflake/BigQuery**: this is a portfolio artifact meant
  to be cloned and run by anyone, immediately, without signing up for
  anything. The models themselves use only standard SQL (`cast`,
  `date_trunc`, `round`, standard joins/aggregates) and would port to a
  warehouse-backed dbt profile with no model changes — just a different
  `profiles.yml` target.
- **Seeds instead of a live source**: in a production pipeline, the four
  `raw_*` tables would be declared as `sources:` landed by an EL tool,
  not committed as CSVs. Seeds are used here purely so the whole project
  is reproducible from a single `git clone`.
